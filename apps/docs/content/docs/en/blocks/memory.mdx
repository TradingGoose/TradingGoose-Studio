The Memory block is designed to store and retrieve conversation messages across workflow executions and supply history to Agent blocks. Its Add operation is currently unavailable; the read and delete operations can manage existing records.

<Callout type="warning">
  Add Memory is currently unavailable through the block: its request omits the `type` and `workflowId` required by the memory endpoint, so adding a message fails. Configuring ID, Role, and Content does not resolve this mismatch. Do not rely on this block to save new conversation history until the implementation is fixed.
</Callout>

## Overview

<Steps>
  <Step>
    <strong>Add Memory</strong>: Currently unavailable; intended to store a message under a named memory ID
  </Step>
  <Step>
    <strong>Get Memory</strong>: Retrieve a single memory entry by its ID
  </Step>
  <Step>
    <strong>Get All Memories</strong>: Fetch up to 50 stored memory records for the current workflow
  </Step>
  <Step>
    <strong>Delete Memory</strong>: Remove a memory entry by ID
  </Step>
</Steps>

## How It Works

Memory entries are stored as chat-style messages with three required fields: an **ID** to scope the memory, a **Role** (`user`, `assistant`, or `system`), and the **Content** text. When you later retrieve memories and pass them into an Agent block's Memories input, the agent sees them as prior conversation turns -- enabling multi-turn dialogue across separate executions.

The intended Add → Agent → Add pattern is blocked by the current Add limitation. Existing records can still be read with Get Memory; pass the returned message array into the Agent's Memories field.

<Callout type="info">
  Memory IDs scope the conversation. Use the same ID across executions to build a continuous conversation history, or use different IDs to maintain separate threads.
</Callout>

## Outputs

| Operation | Output |
|---|---|
| Get Memory | `memories`: message array for the selected ID; `message`: status text |
| Get All Memories | `memories`: up to 50 records shaped as `{ key, type, data }`; `message`: status text |
| Delete Memory | `message`: deletion confirmation |
| Add Memory | Currently fails; see the limitation above |

Get All Memories does not return one flat message array. Select the required record's `data` before using its conversation as Agent memory. No separate top-level `id` is returned.

## Best Practices

- **Use consistent IDs** -- the memory ID is the key that groups messages into a conversation. Use a stable identifier (such as a user ID or session ID) so memories accumulate correctly across runs.
- **Clean up when needed** -- use the Delete operation to clear stale conversations and prevent unbounded memory growth.
