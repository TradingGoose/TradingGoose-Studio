El bloque de flujo de trabajo ejecuta otro flujo de trabajo (secundario) desde dentro del flujo de trabajo actual (principal). Lee el esquema del **Disparador de formulario de entrada** del flujo de trabajo secundario y presenta una interfaz de mapeo para que puedas pasar las variables del padre a las entradas esperadas del secundario. Este es el mecanismo principal para modularizar automatizaciones complejas en subflujos de trabajo reutilizables.

## Descripción general

<Steps>
  <Step>
    <strong>Selecciona un flujo de trabajo secundario</strong>: Elige cualquier flujo de trabajo en tu espacio de trabajo (excepto el actual)
  </Step>
  <Step>
    <strong>Mapea las entradas</strong>: El bloque lee el Disparador de formulario de entrada del secundario y muestra cada campo esperado. Mapea las variables del padre o codifica valores para cada una.
  </Step>
  <Step>
    <strong>Ejecuta</strong>: El flujo de trabajo secundario se ejecuta hasta completarse con las entradas mapeadas
  </Step>
  <Step>
    <strong>Devuelve resultados</strong>: La salida final del secundario se devuelve al padre como la salida `result` del bloque
  </Step>
</Steps>

## Cómo funciona

El flujo de trabajo secundario debe usar un **Disparador de formulario de entrada** como su bloque de inicio. Ese disparador define el esquema de entrada (nombres de campos, tipos y descripciones). Cuando seleccionas el flujo de trabajo secundario en este bloque, la interfaz de mapeo de entradas renderiza dinámicamente esos campos para que puedas conectarlos.

En tiempo de ejecución, el bloque:

1. Resuelve todos los valores mapeados desde el estado actual del flujo de trabajo principal.
2. Invoca al ejecutor del flujo de trabajo secundario, pasando las entradas resueltas.
3. Espera a que el secundario termine.
4. Devuelve `success: true`, `childWorkflowName` y `result` con la salida final del flujo secundario.

<Callout type="info">
  El flujo secundario hereda el destino de ejecución del principal: las ejecuciones del editor usan su grafo guardado actual y las desplegadas usan su versión desplegada. Despliega los cambios del secundario antes de usarlos desde un principal desplegado. El selector excluye el flujo actual; las llamadas anidadas tienen una profundidad máxima de 10.
</Callout>

### Campos

| Campo | Obligatorio | Descripción |
|---|---|---|
| **Seleccionar flujo de trabajo** | Sí | El flujo de trabajo secundario que se va a ejecutar. Debe tener un disparador de formulario de entrada. |
| **Asignación de entradas** | -- | Asignación dinámica de los valores del flujo principal al esquema del disparador del flujo secundario. Aparece después de seleccionar un flujo de trabajo. |

## Salidas

| Salida | Tipo | Descripción |
|---|---|---|
| `success` | boolean | `true` en la ruta normal de éxito |
| `childWorkflowName` | string | Nombre del flujo de trabajo secundario ejecutado |
| `result` | json | La salida final del secundario, no su registro completo de ejecución |

## Buenas prácticas

- **Diseña flujos de trabajo secundarios con disparadores de formulario de entrada claros** -- nombra los campos de forma descriptiva para que la interfaz de asignación sea fácil de usar en el flujo principal.
- **Mantén los flujos de trabajo secundarios enfocados** -- un flujo de trabajo secundario debe hacer bien una sola cosa, lo que lo hace reutilizable en varios flujos principales.
- **Conecta la ruta de error** -- un secundario fallido genera un error de bloque; no devuelve `success: false` a la ruta normal. Conecta la recuperación a la salida de error de Workflow.
