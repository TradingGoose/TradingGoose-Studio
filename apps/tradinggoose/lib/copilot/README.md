# Built-in Copilot

Copilot runs inside Studio. `agent/agent.ts` builds its ordinary Mastra Agent from Studio's tool registry and schemas. `agent/service.ts` handles authenticated application commands, native conversation storage, and tool continuations. Titles and Wand use the same Agent and configured model connections through `native/completion.ts`.

The composer's Provider Options input passes native JSON through the same validator and request path as workflow Agents. Empty input leaves provider defaults unchanged; model changes clear the options. Native run snapshots preserve them through tool suspension and resume. Connection credentials and execution controls remain server-owned.

The shared runtime in `lib/mastra/runtime.ts` passes Studio's `DATABASE_URL` to Mastra's `PostgresStore`, which owns the pool and its idle and checked-out client error guards. Before initialization, its public `stores` map is restricted to the original memory and workflow domain instances, retaining native connection pinning and bounded PostgreSQL deadlock retries. Startup initializes seven native tables in the `mastra` schema: threads, messages, resources, observational memory, memory run fences, workflow snapshots and workflow run owners. Other PostgreSQL domains and automatic thread-state storage are disabled. Failed startup closes storage through `PostgresStore.close()`. Run `bun run db:migrate` separately for application migrations. Copilot and workflow Agents share bounded conversational Memory; the workflow Memory block uses explicit scoped reads and writes on that store.

Native Mastra messages are canonical, including ordered images, tool invocations, results, and provider metadata. Copilot and workflow Agent histories use the same ordered reader and public message projection, exposing parts, tokens, and cost while keeping internal metadata private. Workflow logs reference that history and retain child accounting facts without copying tool transcripts or timing records. Copilot history restores messages and pending tools in one response. Native snapshots own run configuration, approvals, and tool suspensions; supported `listSuspendedRuns`, approval, and resume APIs recover pending work on another Studio instance.

Studio's verification table stores cancellation and dispatch receipts. It stores no copied run configuration, tool arguments, or results. Repeated dispatches are refused. Mastra snapshots store review previews and their base-state hashes; accepted edits recheck that state at the actual write. Browser actions use authoritative Studio readback. Deleting an idle conversation removes its messages, suspended snapshots, and owned application claims.

HTTP cancellation retains thread ownership until the native writer settles and does not undo completed effects. The renewable 15-second thread claim supplies Mastra's native storage fence to generation, approvals, continuations and explicit edits. A successor raises the fence generation, so storage atomically rejects the superseded writer's message and snapshot updates. The service adapts the pinned SDK's async fence scope through its exported, internally marked `setRunFenceContext` API. Crashed runs are marked interrupted; saved history remains available for the next turn.

`lib/mastra/request.ts` prepares generation requests for Copilot, workflow Agents, providers, and other model consumers. It owns connection resolution, validated model/provider options, processors, tracing, and accounting projection. Each model step uses Studio's billing admission and the shared USD calculator: native tokens and standard prices from the pinned `@opencode-ai/models` snapshot. BYOK model estimates use these standard prices for reporting without a Studio model debit. Trusted funding comes from the actual key-selection boundary; Copilot server credentials remain account-funded. Native costs mark report-only BYOK usage with `accountCost: null`; mixed sums preserve the account-funded subtotal through the existing cost aggregation. For direct Studio-account charges, the usage adapter returns the amount accrued after the existing subscription-tier multiplier; reports and native assistant records persist that returned amount. Deferred workflow steps retain their base estimates because the existing workflow settlement quote applies the final multiplier once to the account-funded subtotal, preserving execution fees. Workflow execution logs settle their model charges; standalone calls settle through the same Studio ledger with the existing Copilot subscription-tier multiplier where applicable. Embeddings use the same admission, calculator, and ledger. Missing costs remain unavailable; explicitly free published rates remain valid. Copilot, title, and Wand calls continue when a model price cannot be established: native cost stays unavailable, calls and reported tokens are recorded, and no USD is accrued for that unpriced usage. Known USD costs retain normal accounting and plan multipliers; unrelated model consumers retain their existing accounting rules. Native Mastra assistant-message metadata retains tokens, USD estimates, and cost status through history reload and approval resume. The user-facing MCP endpoint continues to use personal Studio API keys.

System administrators configure Copilot's ordered provider/model list in Admin system settings, and runtime model connections in Admin Services. The catalog starts empty. Its first model is used for initial selection and Wand. The admin picker loads provider identities and model suggestions from Studio's shared `/api/models` endpoint, using Mastra's installed native registry and DB-managed providers. There is no separate Copilot provider list. Admins can enter exact new model IDs; model suggestions and published prices do not gate generation. Provider keys use the existing system-service credential storage, including the shared OpenAI embeddings and Mistral OCR credentials. Each encrypted key is resolved on the server for chat, continuations, titles, and Wand; credentials remain outside persisted run configuration. Public choices have an exact routing ID and a separate provider/model display label, using canonical model metadata where available. Copilot renders the display label for text, icons, tooltips, and accessibility names; gateway routing IDs remain the request and billing identity. The public model list includes configured rows before keys are supplied; missing or cleared required provider keys prevent generation. Configured local endpoints can be keyless. Removing a model prevents new generation and continuation with that model, while history and cancellation remain available. Suspended runs keep their original model identity when the configured list changes.

`lib/mastra/connections.ts` loads managed settings with `resolveSystemServiceSettingsConfig` and credentials with `resolveSystemServiceConfig`. Azure uses the `azure_openai` service's `resourceName`, optional `apiVersion`, exact `deployments` JSON array, and encrypted `apiKey`, routed by native `AzureOpenAIGateway` as `azure-openai/<deployment>`. Ollama and vLLM use their own `baseUrl`, exact `models` JSON arrays, and optional encrypted `apiKey`; each URL includes the OpenAI-compatible `/v1` API path. Additional endpoints use `mastra_model_providers.providers`, a JSON object of `{name,url,models}` entries. Its encrypted `apiKeys` JSON object supplies keys only for custom provider IDs without their own system service; built-in services remain the credential owner for their IDs. Native gateway IDs cannot be repurposed as custom endpoints. The [root runtime guide](../../../../README.md#built-in-ai-runtime) includes the service fields and routing examples. Studio's retired `MASTRA_MODEL_PROVIDERS` and `MASTRA_AZURE_OPENAI` environment configuration is not read; managed settings and credentials stay in the shared DB service layer. Mastra's own provider environment handling and native routing remain unchanged. Public registry reads resolve settings without decrypting credentials and project no connection URLs or secrets. Authorized workflow BYOK overrides remain request-local; Copilot's managed credentials remain account-funded.

Copilot's ordered model list uses the `copilot:setting:configuration` entry in the existing `system_service_values` table. No Copilot column or configuration migration is needed. Admin Services shows Copilot key inputs only for selected native providers, alongside the fixed connection services used elsewhere in Studio. Deselecting a native provider hides its input without deleting its credential. New requests and approval resumes resolve current system-service settings and credentials. Decrypted credentials use the existing Redis JSON cache helpers for 60 seconds, indexed by credential identity and checked against a fingerprint of the current encrypted value. Removed rows cannot use a cached key; rotation cannot reuse a cache entry for the old ciphertext, including after a delayed cache fill. Cache failures use fresh decryption; database failures never authorize from the cache. Already running invocations may finish with their request-local key.

Run focused tests from this application with:

```sh
bun run test lib/copilot/agent lib/copilot/native app/api/copilot stores/copilot
```

Tests use explicit database mocks and Mastra's native `InMemoryStore`, with no database configuration, containers, migrations, or external model-provider contact. Test setup clears `DATABASE_URL` and rejects unmocked PostgreSQL drivers. Native model, approval, history and fresh-context behavior runs against SDK in-memory storage; PostgreSQL persistence and cross-process transaction guarantees are not exercised by this suite. Run `bun run type-check` and `bun run build` sequentially because Next.js regenerates build types.

Smoke-test configured models, chat/history/attachments, titles, Wand, approvals/previews, browser business flows, and cancellation before cutover. The generated migration drops the retired application Copilot and workflow memory tables; it does not backfill their data. Revert the application before migration, or restore a database backup when rolling back after migration.
