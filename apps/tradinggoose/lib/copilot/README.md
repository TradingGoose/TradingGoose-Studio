# Built-in Copilot

The Copilot worker runs the model loop. `agent/agent.ts` builds its ordinary Mastra Agent from Studio's tool registry and schemas. `agent/service.ts` handles authenticated application commands, native conversation storage, and tool continuations. Titles and Wand use the same Agent and native model connections through `native/completion.ts`.

Messages and tool continuations are admitted as background jobs, then observed through Mastra's native `subscribeToThread` stream. They use the `copilot-execution` Trigger.dev task or the same executor in a long-running local application process. Each Trigger job inherits the project's default 600-second duration and runs once; Copilot does not enter the workflow pending queue or its tier-backed backlog, concurrency, and duration checks. Workflow and indicator executions retain those checks. Copilot's model usage admission and account charges still apply.

Studio runs server tools, approved edits, and authoritative readbacks through its signed `/api/copilot/native/tool` endpoint. The worker suspends the native call before transferring its thread claim. Studio resolves the saved arguments and renews the successor claim until the tool settles, including after Stop. It streams a heartbeat every 25 seconds and returns the generation the worker must reclaim before resuming the model.

Local workers connect to the long-running Studio listener on `127.0.0.1` at `PORT` (default 3000). Trigger workers use `NEXT_PUBLIC_APP_URL` or, if configured, `COPILOT_STUDIO_ORIGIN` to reach Studio. Keep ingress streaming enabled. GCE's chart binds the app Service to a 660-second BackendConfig.

Run the same revision of Studio and its Trigger workers with shared `DATABASE_URL`, `REDIS_URL`, signing secrets and business-service configuration. Mastra's `RedisStreamsPubSub` carries native output across processes. PostgreSQL owns conversation history and snapshots. Browser reloads reconnect to the existing thread stream, and crashed runs are reported as interrupted. Native thread metadata stores the current background job identity and outcome.

The shared runtime in `lib/mastra/runtime.ts` passes Studio's `DATABASE_URL` to Mastra's `PostgresStore`, which owns the pool and its idle and checked-out client error guards. Before initialization, its public `stores` map is restricted to the original memory and workflow domain instances, retaining native connection pinning and bounded PostgreSQL deadlock retries. Startup initializes seven native tables in the `mastra` schema: threads, messages, resources, observational memory, memory run fences, workflow snapshots and workflow run owners. Other PostgreSQL domains and automatic thread-state storage are disabled. Failed startup closes storage through `PostgresStore.close()`. Run `bun run db:migrate` separately for application migrations. Copilot and workflow Agents share bounded conversational Memory; the workflow Memory block uses explicit scoped reads and writes on that store.

Native Mastra messages are canonical, including ordered images, tool invocations, results, and provider metadata. Copilot and workflow Agent histories use the same ordered reader and public message projection, exposing parts, tokens, and cost while keeping internal metadata private. Workflow logs reference that history and retain child accounting facts without copying tool transcripts or timing records. Copilot history restores messages and pending tools in one response. Native snapshots own run configuration, approvals, and tool suspensions; supported `listSuspendedRuns`, approval, and resume APIs recover pending work on another Studio instance.

Studio's verification table stores cancellation and dispatch receipts. It stores no copied run configuration, tool arguments, or results. Repeated dispatches are refused. Mastra snapshots store review previews and their base-state hashes; accepted edits recheck that state at the actual write. Browser actions use authoritative Studio readback. Deleting an idle conversation removes its messages, suspended snapshots, and owned application claims.

HTTP cancellation retains thread ownership until the native writer settles and does not undo completed effects. The renewable 15-second thread claim supplies Mastra's native storage fence to generation, approvals, continuations and explicit edits. A successor raises the fence generation, so storage atomically rejects the superseded writer's message and snapshot updates. The service adapts the pinned SDK's async fence scope through its exported, internally marked `setRunFenceContext` API. Crashed runs are marked interrupted; saved history remains available for the next turn.

`lib/mastra/request.ts` prepares generation requests for Copilot, workflow Agents, providers, and other model consumers. It owns connection resolution, validated model settings, processors, tracing, and accounting projection. Each model step uses Studio's billing admission and the shared USD calculator: native tokens and standard prices from the pinned `@opencode-ai/models` snapshot. BYOK model estimates use these standard prices for reporting without a Studio model debit. Trusted funding comes from the actual key-selection boundary; Copilot server credentials remain account-funded. Native costs mark report-only BYOK usage with `accountCost: null`; mixed sums preserve the account-funded subtotal through the existing cost aggregation. For direct Studio-account charges, the usage adapter returns the amount accrued after the existing subscription-tier multiplier; reports and native assistant records persist that returned amount. Deferred workflow steps retain their base estimates because the existing workflow settlement quote applies the final multiplier once to the account-funded subtotal, preserving execution fees. Workflow execution logs settle their model charges; standalone calls settle through the same Studio ledger with the existing Copilot subscription-tier multiplier where applicable. Embeddings use the same admission, calculator, and ledger. Missing costs remain unavailable; explicitly free published rates remain valid. Copilot, title, and Wand calls continue when a model price cannot be established: native cost stays unavailable, calls and reported tokens are recorded, and no USD is accrued for that unpriced usage. Known USD costs retain normal accounting and plan multipliers; unrelated model consumers retain their existing accounting rules. Native Mastra assistant-message metadata retains tokens, USD estimates, and cost status through history reload and approval resume. The user-facing MCP endpoint continues to use personal Studio API keys.

System administrators configure Copilot's ordered provider/model list in Admin system settings, and provider API keys in Admin Services. The catalog starts empty. Its first model is used for initial selection and Wand. The admin picker loads provider identities and model suggestions from Studio's shared `/api/models` endpoint, using Mastra's native `GatewayRegistry`. The shared provider list includes Mastra’s `models.dev` integrations that accept an API key without deployment-specific URL settings. Separately configured gateways such as Netlify and Azure are unsupported; OpenRouter and Vercel remain available through Mastra’s native `models.dev` integration. Admins can enter exact new model IDs; model suggestions and published prices do not gate generation. Provider keys use the existing system-service credential storage, including the shared OpenAI embeddings and Mistral OCR credentials. Each encrypted key is resolved on the server for chat, continuations, titles, and Wand; credentials remain outside persisted run configuration. Public choices have an exact routing ID and a separate provider/model display label, using canonical model metadata where available. Copilot renders the display label for text, icons, tooltips, and accessibility names; gateway routing IDs remain the request and billing identity. The public model list includes configured rows before keys are supplied; missing or cleared required provider keys prevent generation. Removing a model prevents new generation and continuation with that model, while history and cancellation remain available. Suspended runs keep their original model identity when the configured list changes.

`lib/mastra/connections.ts` resolves each native provider's current system-service credential with `resolveSystemServiceConfig`. Public registry reads use Mastra metadata and credential-presence flags without decrypting keys. Authorized workflow BYOK overrides remain request-local; Copilot's managed credentials remain account-funded.

Copilot and workflow Agents show the selected model’s Mastra Code SDK levels. The workflow picker is under Additional Fields. Both send the selected level through the same MastraCodeGateway request. Mastra controls the agent loop. The composer saves the model and selection for the current actor and workspace on this device. Studio validates each new turn against the configured models. Approval and result continuations use the selection from the original native run and resolve the current credential before inference.

Copilot's ordered model list uses the `copilot:setting:configuration` entry in the existing `system_service_values` table. No Copilot column or configuration migration is needed. Admin Services shows Copilot key inputs only for selected native providers, alongside the fixed services used elsewhere in Studio. Deselecting a native provider hides its input without deleting its credential. New requests and approval resumes resolve current system-service settings and credentials. Credentials remain encrypted in the database and are decrypted on each resolution; decrypted values are not cached. Removed or rotated keys take effect on the next resolution. Already running invocations may finish with their request-local key.

Run focused tests from this application with:

```sh
bun run test lib/copilot/agent lib/copilot/native app/api/copilot stores/copilot
```

Tests use explicit database mocks and Mastra's native `InMemoryStore`, with no database configuration, containers, migrations, or external model-provider contact. Test setup clears `DATABASE_URL` and rejects unmocked PostgreSQL drivers. Native model, approval, history and fresh-context behavior runs against SDK in-memory storage; PostgreSQL persistence and cross-process transaction guarantees are not exercised by this suite. Run `bun run type-check` and `bun run build` sequentially because Next.js regenerates build types.

Smoke-test configured models, chat/history/attachments, titles, Wand, approvals/previews, browser business flows, and cancellation before cutover. The generated migration drops the retired application Copilot and workflow memory tables; it does not backfill their data. Revert the application before migration, or restore a database backup when rolling back after migration.
