### Design Decisions
- Listing identity and display data have separate owners: persist and transport `ListingIdentity`, then resolve `ListingResolved` only at a display/search boundary. A resolved aggregate is not a substitute for the stored identity.
- Zod schemas reject malformed, extra, or incomplete identity/document data at boundaries rather than silently filling defaults or carrying display fields through persistence.
- Shared batch resolution is preferred over per-component resolution caches so each UI surface uses the same identity-keyed data flow and can show an explicit fallback without mutating the source identity.
- Folder hierarchy invariants are checked inside the same workspace lock as the write, avoiding races between sibling ordering, moves, and deletes.
- Airtable retains a committed receipt when a later poll page cannot be fetched, but integrity/ownership failures remain terminal; Microsoft Graph validation is intentionally limited to the Teams callback namespace to avoid accepting arbitrary webhook-path collisions.

### Future Branch Guardrails
- A listing search result is display data. When a monitor, watchlist, widget, order, query filter, or provider request needs a listing, pass only its strict `listingIdentity` and resolve presentation separately.
- Do not use Zod passthrough schemas, default-filling normalizers, or object spreads to preserve display metadata in monitor documents, widget params, watchlists, or market requests.
- Keep display consumers on `ListingResolved` and identity-only consumers on `ListingIdentity`; use `useResolvedListings()` or the resolve helpers rather than adding independent component caches.
- Keep every folder write under `lockFolderWrites()` and preserve the one-level root-to-child hierarchy. New mutation routes must validate workspace ownership inside the transaction.
- Generate Teams chat callback paths only with `generateMicrosoftTeamsChatCallbackPath()`, and keep validation-token responses scoped to recognized Teams chat callbacks.
- Preserve Airtable's typed integrity failures and durable receipt behavior: retry transient page failures, execute already committed payloads, enqueue the returned continuation, and do not downgrade ownership/integrity errors into a successful execution.
