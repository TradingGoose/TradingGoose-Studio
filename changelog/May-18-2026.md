## refactor/execution @ 82a8f7b8 vs origin/staging

### Summary
- Simplifies queued execution so `pending_execution` is a lease queue for active work only, while `workflow_execution_logs` owns durable terminal state, results, errors, timing, cost, files, and response-block metadata.
- Centralizes workflow event reconstruction in `apps/tradinggoose/lib/execution/workflow-execution-events.ts` so job status, SSE streams, public API waits, and access checks read one shared execution state contract.
- Reworks pending execution draining to serialize work per billing scope, defer capacity-blocked starts with a short retry, wake duplicate ordered rows, and avoid storing terminal results in queue rows.
- Tightens workflow logging so logs are opened before execution, terminalized on usage/logging failures, and completed with explicit success/error state instead of inferring failure from trace spans.

### Key Changes
- `packages/db/schema/workflows.ts` removes terminal states from `pendingExecutionStatusEnum`; `pending_execution.status` is now only `'pending' | 'processing'`. The `pending_execution` columns `attempts`, `errorMessage`, `result`, and `completedAt` are removed so queue rows no longer store terminal outcomes.
- `apps/tradinggoose/lib/execution/pending-execution.ts` makes `enqueuePendingExecution()` the canonical insert/wake path. It resolves billing scope through `resolveServerExecutionBillingContext()`, enforces per-tier pending limits, cleans stale pending rows, skips duplicate pending ids, skips workflow ids already present in `workflowExecutionLogs`, and prevents overlapping active rows for the same `orderingKey`.
- `triggerPendingExecutionDrain()` in `apps/tradinggoose/lib/execution/pending-execution.ts` centralizes worker wake-up behavior for Trigger.dev and local development. On a duplicate ordered row, `enqueuePendingExecution()` now returns `inserted: false` but still wakes the drain so previously blocked work can continue.
- `claimNextPendingExecution()` now claims only ready pending rows by billing scope and lease status. Ordering-key overlap is enforced at insert time instead of through claim-time subqueries, keeping the drain responsible for one active row per billing scope/order key.
- `completePendingExecution()` now deletes queue rows because terminal state belongs to execution-specific owners. `deferPendingExecutionStart()` replaces retry/failure state mutation by returning a blocked row to `pending` with `nextAttemptAt = now + START_BLOCKED_RETRY_DELAY_MS`.
- `cancelPendingWorkflowExecution()` in `apps/tradinggoose/lib/execution/pending-execution.ts` now only marks pending/processing workflow payloads with `cancelRequestedAt` and returns `cancelling` or `not_found`. It no longer writes cancelled terminal results into `pending_execution`.
- `apps/tradinggoose/background/pending-execution-drain.ts` drains a billing scope until empty or start-blocked. It dispatches workflow, webhook, schedule, indicator monitor, and document rows through their type-specific handlers, deletes successful and terminally failed queue rows, and defers start-blocked rows for concurrency/backend/local saturation or `WorkflowLogStartError`.
- `apps/tradinggoose/background/pending-execution-drain.ts` also routes terminal document dispatch failures through `failQueuedDocumentProcessingJob()`, which calls `markDocumentProcessingFailed()` in `apps/tradinggoose/lib/knowledge/documents/service.ts` before deleting the queue row.
- `apps/tradinggoose/lib/execution/workflow-execution-events.ts` now owns `readWorkflowExecutionAccessContext()`, `createWorkflowExecutionResultFromLog()`, and `readWorkflowExecutionEventState()`. These helpers read active queue rows, buffered Redis/local events, terminal stream events, and `workflowExecutionLogs` so callers can reconstruct completed, failed, cancelled, and still-processing workflow state from one module.
- `createWorkflowExecutionResultFromLog()` reconstructs public `ExecutionResult` state from `workflowExecutionLogs.executionData.finalOutput`, `traceSpans`, `hasResponseBlock`, `errorMessage`, timing fields, and queued child metadata. A successful workflow output containing an `error` property is preserved as successful output unless the log level is `error`.

It formats completed workflow jobs through `createPublicExecutionResult()` or `createInternalWorkflowJobResult()` only for matching internal child workflow polls.

### Design Decisions
- `pending_execution` is intentionally lease-only. Queue rows represent work that can still be claimed or cancelled; once a handler reaches a terminal outcome, durable state must live in the execution owner, primarily `workflowExecutionLogs` for workflows and document processing fields for knowledge documents.
- Workflow status reconstruction is centralized in `workflow-execution-events.ts` because active queue rows, event buffers, and durable logs all describe the same execution id at different lifecycle phases. Routes should not duplicate fallback logic for pending row vs log row vs event buffer.
- Logging starts before usage checks and block execution so every queued workflow has a durable terminal row even when billing, usage, env decrypt, start-block resolution, executor setup, block execution, or log completion fails after the queue row was claimed.
- `WorkflowLogStartError` is treated as start-blocked by the drain because a workflow without a durable log cannot safely execute. Deferring preserves the queue row for a later attempt instead of running blocks without terminal state.
- Cancellation is cooperative. API deletion marks `cancelRequestedAt` in the queue payload, and the executor checks `isPendingWorkflowExecutionCancellationRequested()`; terminal cancellation is emitted by the workflow job/log flow rather than pre-writing a fake failed result in the queue.
- Stream writers are only created for `stream: true` queued payloads. Non-stream jobs avoid transient event buffer requirements and rely on `workflowExecutionLogs` for terminal API/job responses.
- Successful workflow output is not classified by the presence of an `error` field in user output. `ExecutionLogger.completeWorkflowExecution()` receives explicit `success`, and reconstructed job responses use the durable log level.
- Ordered producers such as schedules and indicator monitors intentionally skip active duplicates and wake the drain. This keeps one active row per ordered source while avoiding additional backfill or legacy retry paths.

### Removed or Replaced Items
- Do not reintroduce `pending_execution.status` values `completed` or `failed`. Use `workflowExecutionLogs.level`, `workflowExecutionLogs.endedAt`, and `workflowExecutionLogs.executionData` for workflow terminal state.
- Do not reintroduce `pending_execution.attempts`, `pending_execution.error_message`, `pending_execution.result`, or `pending_execution.completed_at`. Queue rows should be deleted on terminal completion and deferred with `nextAttemptAt` only when start capacity is blocked.
- Do not reintroduce `PENDING_EXECUTION_RETRY_DELAY_MS`, `retryPendingExecution()`, or `failPendingExecution()` in `apps/tradinggoose/lib/execution/pending-execution.ts`. Use `START_BLOCKED_RETRY_DELAY_MS`, `deferPendingExecutionStart()`, and execution-owner terminal state instead.
- Do not reintroduce `WORKFLOW_EXECUTION_CANCELLED_ERROR` as queue-row state. Cancellation is represented by `payload.cancelRequestedAt`, executor cancellation checks, and `execution:cancelled` terminal events/log reconstruction.
- Do not reintroduce `readPendingWorkflowExecutionAccessContext()` from `apps/tradinggoose/lib/execution/pending-execution.ts`. Use `readWorkflowExecutionAccessContext()` from `apps/tradinggoose/lib/execution/workflow-execution-events.ts` so completed executions remain readable after queue-row deletion.
- Do not restore the `enabled` parameter on `createWorkflowExecutionEventWriter()`. Callers should only create a writer when streaming is requested.
- Do not restore trace-span-derived success detection in `apps/tradinggoose/lib/logs/execution/logger.ts` or `LoggingSession`. Use explicit `success` and `errorMessage` from the execution result.
- Do not pass encrypted variables into `createEnvironmentObject()` at log start. Variables are merged into execution metadata at completion through `LoggingSession.complete()` and `completeWithError()`.
- Do not restore schedule or indicator-monitor duplicate queue behavior that increments dispatched counts for `inserted: false`; those active ordered rows are intentional skips plus drain wakeups.

### Future Branch Guardrails
- Treat `pending_execution` as a queue lease table only. New features must not add durable result, retry, error, or completion columns back to the queue.
- If an execution endpoint needs current or terminal workflow status, import `readWorkflowExecutionEventState()` or `createWorkflowExecutionResultFromLog()` instead of querying pending rows and logs independently.
- If an endpoint needs stream authorization, import `readWorkflowExecutionAccessContext()` from `workflow-execution-events.ts`; do not require a live queue row for completed workflow streams.
- Any workflow execution path that can run blocks must open a `LoggingSession` first and pass the returned `workflowLogId` into executor context. If log start fails, defer the queue row rather than executing without durable terminal state.
- Preserve cooperative cancellation: request cancellation through `cancelPendingWorkflowExecution()`, check it through `isPendingWorkflowExecutionCancellationRequested()`, and emit/log terminal cancellation from workflow execution.
- Keep start-blocked errors limited to execution concurrency limit errors, concurrency backend unavailability, local VM saturation, and `WorkflowLogStartError`. Other handler errors should be terminal for that queue row and recorded by the execution owner.
- Use `orderingKey` for producers that should collapse overlap, and treat `inserted: false` as a non-dispatch outcome. Do not add separate dedupe tables or legacy backfill paths.
- Do not make non-stream workflow runs depend on the transient event buffer. Durable terminal reads should work from `workflowExecutionLogs` even when Redis/local event buffers are gone.
- Keep response-block detection durable by writing `hasResponseBlock` into log execution data and reading `metadata.hasResponseBlock` in `workflowHasResponseBlock()`.
- Do not edit generated migration files by hand. Schema changes belong in `packages/db/schema/workflows.ts`, with migrations generated by the existing database tooling.
