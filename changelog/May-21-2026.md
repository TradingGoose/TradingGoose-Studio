### Design Decisions
- `listingIdentity` is intentionally modeled as a value type rather than another `json` convention. The exact four-field identity shape is now the durable data contract, while UI metadata such as `base`, `quote`, `name`, `assetClass`, and icons remains resolved display data.
- Strict runtime ingestion belongs to `parseListingIdentityValueStrict()` in `apps/tradinggoose/lib/listing/identity.ts`. Optional UI hydration and permissive normalization can still use `toListingValueObject()`, but tool execution, workflow inputs, variables, and response conversion should fail early on invalid listing identity payloads.
- Tool schemas intentionally reuse `LISTING_IDENTITY_JSON_SCHEMA` for both LLM-visible and execution schemas so the model, executor, and tool registry agree on required fields and allowed `listing_type` values.
- Reference filtering intentionally moved from `requiredOutputShape='listingIdentity'` to `allowedOutputTypes`. Listing identity eligibility is now driven by output/variable type metadata, not by assuming an output named `listing` plus sibling `listingBase` and `listingQuote` fields.
- Workflow variables intentionally support listing identity through the existing `VariableManager` and Yjs validation paths instead of adding a separate listing-variable subsystem.
- Input trigger and response builder parsing intentionally preserve workflow reference strings. A literal listing identity must validate immediately, but `<...>` references should be resolved by the existing workflow reference pipeline.

### Design Decisions
- Streaming belongs on the queue response because the queue route already owns authentication, workspace access, write permission checks, pending execution creation, and task IDs. Keeping the stream on `POST /api/workflows/[id]/queue` avoids a second GET route that must reconstruct the same execution/access context.
- Console stream buffering belongs in `apps/tradinggoose/stores/console/store.ts`, not `useWorkflowExecution()`. The store owns entry lifetime and can clear stream buffers when entries are removed, a block reaches a terminal state, or an execution completes/cancels/errors.
- Console entry matching is intentionally execution-aware. Repeated loop and parallel blocks can emit multiple runs for the same `blockId`, so matching uses `workflowId`, `executionId`, `blockId`, `startedAt`, and iteration context before falling back to a running entry.
- Server-side agent blocks call provider executors directly to avoid a server-to-server HTTP loop through the provider API. Browser callers keep the HTTP path, but server execution now shares the same provider request, API key, model, timing, and cost contracts directly.
- Provider helpers intentionally separate requested model identity from provider API model names. Cost summaries and response metadata use `request.model`, while provider clients can pass a normalized `apiModel` to the external API.
- JSON rendering is intentionally shared outside the workflow console widget. Records trace spans, console output details, and future JSON surfaces should reuse the same redaction, copy text, raw/structured modes, wrapping, and listing identity behavior.
- Workflow value-type ownership moved to `apps/tradinggoose/lib/workflows/value-types.ts` because blocks, tools, triggers, variables, providers, widgets, and executor validation were maintaining parallel string unions.
- Unsupported block and variable value types intentionally fail fast. This project has no legacy compatibility requirement, and silently coercing invalid contracts to `string` would hide broken tool/provider definitions.
- Records fallback state intentionally stays inside `LogDetails` and `OrderDetails` shells so navigation, close actions, mode switching, and provider/order metadata remain available while linked log data is loading or unavailable.
