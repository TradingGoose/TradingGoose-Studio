### Design Decisions
- `listingIdentity` is intentionally modeled as a value type rather than another `json` convention. The exact four-field identity shape is now the durable data contract, while UI metadata such as `base`, `quote`, `name`, `assetClass`, and icons remains resolved display data.
- Strict runtime ingestion belongs to `parseListingIdentityValueStrict()` in `apps/tradinggoose/lib/listing/identity.ts`. Optional UI hydration and permissive normalization can still use `toListingValueObject()`, but tool execution, workflow inputs, variables, and response conversion should fail early on invalid listing identity payloads.
- Tool schemas intentionally reuse `LISTING_IDENTITY_JSON_SCHEMA` for both LLM-visible and execution schemas so the model, executor, and tool registry agree on required fields and allowed `listing_type` values.
- Reference filtering intentionally moved from `requiredOutputShape='listingIdentity'` to `allowedOutputTypes`. Listing identity eligibility is now driven by output/variable type metadata, not by assuming an output named `listing` plus sibling `listingBase` and `listingQuote` fields.
- Workflow variables intentionally support listing identity through the existing `VariableManager` and Yjs validation paths instead of adding a separate listing-variable subsystem.
- Input trigger and response builder parsing intentionally preserve workflow reference strings. A literal listing identity must validate immediately, but `<...>` references should be resolved by the existing workflow reference pipeline.
