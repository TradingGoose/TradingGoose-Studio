### Design Decisions
- `listingIdentity` is intentionally modeled as a value type rather than another `json` convention. The exact four-field identity shape is now the durable data contract, while UI metadata such as `base`, `quote`, `name`, `assetClass`, and icons remains resolved display data.
- Strict runtime ingestion belongs to `parseListingIdentityValueStrict()` in `apps/tradinggoose/lib/listing/identity.ts`. Optional UI hydration and permissive normalization can still use `toListingValueObject()`, but tool execution, workflow inputs, variables, and response conversion should fail early on invalid listing identity payloads.
- Tool schemas intentionally reuse `LISTING_IDENTITY_JSON_SCHEMA` for both LLM-visible and execution schemas so the model, executor, and tool registry agree on required fields and allowed `listing_type` values.
- Reference filtering intentionally moved from `requiredOutputShape='listingIdentity'` to `allowedOutputTypes`. Listing identity eligibility is now driven by output/variable type metadata, not by assuming an output named `listing` plus sibling `listingBase` and `listingQuote` fields.
- Workflow variables intentionally support listing identity through the existing `VariableManager` and Yjs validation paths instead of adding a separate listing-variable subsystem.
- Input trigger and response builder parsing intentionally preserve workflow reference strings. A literal listing identity must validate immediately, but `<...>` references should be resolved by the existing workflow reference pipeline.

### Design Decisions
- Console stream buffering intentionally belongs to `apps/tradinggoose/stores/console/store.ts`, not `useWorkflowExecution()`. The store has the full persisted entry list and can clear stream buffers when entries are removed, when a block finishes, or when an execution reaches a terminal event.
- `ingestWorkflowExecutionEvent()` intentionally updates entries by stable execution metadata instead of only `blockId`. A repeated loop/parallel block can emit multiple runs under the same block ID, so matching must include `executionId`, `startedAt`, and iteration context.
- Live workflow runs intentionally request streaming unconditionally. The console, chat callers, and selected-output callers now see the same event flow and do not rely on a request-level `stream` toggle.
- JSON rendering is intentionally shared outside the workflow console widget. Records trace spans, console output details, and future JSON surfaces should share redaction, copy text, raw/structured modes, wrapping, and listing identity display behavior.
- `WorkflowValueType` ownership intentionally moved to `apps/tradinggoose/lib/workflows/value-types.ts` because workflow value types are shared by blocks, tools, triggers, variables, providers, widgets, and executor validation. Local unions were already diverging as listing identity support expanded.
- Unsupported block/variable value types intentionally throw instead of coercing to a fallback type. The project has no legacy compatibility requirement, and silent `string` fallback would hide invalid tool or provider contracts.
- Listing display row ownership intentionally lives under `apps/tradinggoose/components/listing-selector/listing/row.tsx` because selector widgets and JSON listing identity display need the same symbol/company/avatar/flag/asset-class rendering rules.
- Records order log fallback intentionally stays inside `OrderDetails` with the header still rendered. A missing linked log should not trap the user away from Order data, Provider, navigation, or Close controls.
